# 应用拦截与风控

应用可能把注入输入、无障碍连接和虚拟屏识别为自动化，后果最重会落在**用户的真实账号**上。先例：2025 年 12 月豆包手机助手上线后，微信触发风控，用户被强制下线甚至封号；部分银行 App 要求先关闭助手，支付宝、淘宝拒绝访问。

本 Skill 的处理方式是让用户知情并同意，**不做反检测**。主要场景是测试自己开发的应用；测第三方敏感应用时，建议用测试账号或测试机。

## 敏感应用：sensitive_app

open 在判定为敏感应用时，不建屏、不启动应用，直接返回 `category`、`appLabel`、`askUser`。判定依据有两条：
- 电脑端的包名单，见 android.py 的 `SENSITIVE_PACKAGES`，外加包名里含 bank、wallet 等词。
- 手机端读到的应用名里含"银行""证券""支付"等词。

名单不完整，名单外的应用明显涉及钱或账号时，同样先提醒用户。

1. 把 `askUser` 原样或改写后告诉用户，等用户答复。
2. 用户明确同意后，重新 open，加 `--accept-risk`。建议同时加 `--no-accessibility`：会话全程不连接无障碍，被察觉的面最小。
3. `--no-accessibility` 下，`layout`、`--target`、`--ref`、`--settle`、`text`、`--annotate` 都会返回 `accessibility_disabled`，只能截图、点坐标、滑动、按键。

## 发现被拦截时

信号：
- 返回里出现 `riskSignals`，即命中了风控提示词。提示词列表是人工整理的，只作提示，要看截图确认。
- 截图里出现"环境异常""请关闭无障碍/辅助功能""检测到自动化""被迫下线""账号异常"之类的提示。
- 以下错误也可能是应用的防护造成的，需要结合截图判断：`set_text_failed`（安全键盘）、`layout_unavailable`（屏蔽了读取）、`blankFrame: "dark"`（防截屏）。

处理：
1. 立即停止操作。不重试，也不换方式绕过：重试会加重账号风险。
2. `close --reason app_blocked`。
3. 按下面的模板告诉用户：

```text
测试没能继续：<应用名（包名）> 拦截了自动化操作。
- 停在哪一步：<步骤>
- 看到了什么：“<提示原文>”（截图：<路径>）
- 判断：<确定 / 可能> 是应用识别到了 <无障碍 / 模拟点击 / 后台屏>；<依据>
- 已做的处理：会话已关闭，没有重试，也没有尝试绕过
- 对你账号的影响：<有没有被下线 / 看不出影响>；建议 <检查账号状态 / 改用测试账号或测试机 / 这一步手动完成>
```

只是功能受限、没有风控迹象时（比如截图全黑），用 `userMessage` 加上你看到的情况说明原因，不要只报错误码。
